# 0067: Rulebook and "Why?" v1

Status: Proposed
Date: 2026-10-29
Plan step: `plans/platform-v5.md`, workstream X2. Spec: `docs/spec/02-features.md` F-S5 (v1 part), `docs/spec/01-product-direction.md`
decision 11, `docs/spec/03-data-model.md` (`rulebook_entry`), `docs/spec/articles/JSY-SS-01/rulebook.md`.

## Context

Spec decision 11 says every check, range, option and tech-pack value explains itself through Knitwright's rulebook, and the AI
may only phrase what is written there. Before any AI (Z2), the platform needs the rulebook as data, a way to read a rule by id,
a "Why?" link that shows it, a record of ids that have no rule yet, and a page where the team edits and confirms rules.

## Decision

1. **Two tables** (`supabase/migrations/20261101020000_rulebook.sql`).
   - `rulebook_entries`: one row per **version** of a rule. Unique `(rule_id, version)`; `rule_id` matches `R-<FAMILY>-<NNN>`.
     Columns: `topic` (construction | fabric | print | fit | grading | labels | qc | cost | pattern | personalisation; null only for
     R-GAP-000), `article_codes text[]` (empty = every article), `title`, `rule`, `body`, `best_practice`, `source`
     (factory | pattern_master | standard | knitwright), `source_note`, `status` (draft | confirmed), `confirmed_by`, `confirmed_at`,
     `created_by`, `created_at`.
   - `rulebook_gaps`: one row per code with no entry: `context` (latest non-empty), `count`, `first_seen`, `last_seen`.
2. **Never overwritten.** A trigger refuses delete, truncate and every update except (a) draft to confirmed with the words
   unchanged and (b) `created_by` / `confirmed_by` set to null when that account is erased. An edit is
   `rulebook_entry_save(actor, …)`, which adds `max(version) + 1` as a draft under an advisory lock. The newest version is the
   one in force (`latestOf`, `resolveRule`); earlier versions are listed on the admin page.
3. **Access.** Signed-in users SELECT `rulebook_entries` through a column grant that leaves out `created_by` and `confirmed_by`
   (as finding L8 did for templates); visitors get nothing. `rulebook_gaps` has no browser grant or policy. The server's key holds
   SELECT on both. `rulebook_entry_save` and `rulebook_entry_confirm` are service-role only and answer `P0002` unless the actor is
   in `platform_admins`; `rulebook_gap_log(code, context)` is service-role only and is called by the "Why?" action for any
   signed-in person (rate limit `read`). That action logs a gap only for an id of the form `R-<FAMILY>-<NNN>`: an id of any
   other shape still shows the gap text, so nobody can fill the gap list with made-up codes through the one write a member
   can reach. `logGap` itself takes any code, because a check code the platform's own code meets need not look like a rule id.
4. **Seed.** All 45 rules of the JSY-SS-01 rulebook, word for word, version 1, status draft, plus `R-GAP-000` ("No rule written
   yet; the team has been told", the plan's words; title "A check with no rule yet"). Mapping from the rulebook's columns:

   | Rulebook column | Column |
   |---|---|
   | ID | `rule_id` |
   | Applies to | `title` |
   | Rule | `rule` |
   | Why | `body` |
   | Best practice | `best_practice` |
   | Source (as written) | `source_note` |
   | Source, sorted | `source`: "Knitwright…" is `knitwright`; "Factory…" or a price list is `factory`; anything else (industry, process, regulation, AQL practice) is `standard`. None is `pattern_master` yet. |
   | Status | `status` = `draft` |
   | Section | `topic`: R-PAT pattern, R-FIT fit, R-CON construction, R-SUB print, R-PER personalisation, R-LAB labels, R-QC qc, R-COST cost |

   R-SUB, R-LAB, R-QC and R-COST are "shared by every sublimated article", so they carry no article code; the other families carry
   `JSY-SS-01`. The seed was generated by `lib/rulebook/markdown.ts` from the spec file; `lib/rulebook/seed.test.ts` checks every
   tuple in the migration against a fresh reading of the spec file, and `tests/integration/rulebook.test.ts` checks the loaded rows.
   The spec's data model calls the confirmer `approved_by`; it is `confirmed_by` here because the plan names the status
   "confirmed".
5. **Code.** `lib/rulebook`: `resolveRule(client, ruleId)`, `rulesFor(client, { articleCode, topic })`, `logGap(admin, { code,
   context })`, `loadEntries`, `loadGaps`, `saveEntry`, `confirmEntry`, the pure `latestOf` / `selectRules` / `whyView`, and the
   actions `explainRuleAction` (any signed-in user), `saveRuleAction` and `confirmRuleAction` (platform admins,
   `assertPlatformAdmin`). `lib/rulebook/constants.ts` holds no zod so client components can import it.
6. **UI.** `components/rulebook/WhyLink` (`<WhyLink ruleId context? />`): a button "Why?" named "Why? Rulebook <id>", with
   `aria-haspopup="dialog"`, `aria-expanded` and `aria-controls`; it opens a non-modal dialog labelled by the rule's heading that
   takes focus, closes on Escape, Close or the button, and gives focus back. It shows title, rule, why, best practice, source and
   status ("Draft, not yet confirmed by the factory" or "Confirmed by the factory on <date>"). An unknown id shows only the gap
   text and is logged. `/admin/rulebook` (platform admins; 404 for everyone else) lists the newest version of every rule by topic
   with its Why?, "Edit as a new version", "The factory confirmed version N", earlier versions, the gap list, an "Add a rule" form
   and a "Try a Why? link" box. The ops console's nav has one new entry, "Rulebook".
7. **Wording.** The rulebook is the one place where "confirmed" is allowed to mean something settled, because it is the
   factory signing off one *rule's words*, never a design, a measurement or a tech-pack value. `lib/rulebook` is added to the
   folders `lib/techpack/wording.test.ts` scans, with three sentences listed as allowed: "Draft, not yet confirmed by the
   factory" (says the sign-off has not happened), "Confirmed by the factory on …" and "The factory confirmed version N" (both
   shown only from the record that holds who and when, as the tech pack's "Reviewed by … on …" is).

## Honest limits

- No feature calls `<WhyLink>` yet: findings, ranges, options and tech-pack fields get their rule ids in X1, X4 and Y4. Until then
  the only Why? links are on the admin page.
- `rulesFor` reads the whole table and filters in TypeScript; fine for hundreds of rows, to revisit past a few thousand.
- The newest version is shown even when it is a draft and an earlier version was confirmed; the popover then says "Draft".
- Confirming is recorded by a platform admin on the factory's behalf; there is no factory sign-in or initials field yet.
- Names on the admin page are sign-in addresses, as on `/admin/settings`.

## Owner questions

1. Should a "Why?" show the newest confirmed version when the newest version is still a draft?
2. Is "every article" right for the shared R-SUB, R-LAB, R-QC and R-COST rules, or should they list only sublimated articles?
3. Is the source sorting right, in particular "Supplier price lists, May 2026" (R-COST-003) as `factory` and "Grading practice"
   (R-FIT-003) as `standard` rather than `pattern_master`?
4. Should a confirmation record the factory person's name (pattern master, production manager) as the rulebook's sign-off column asks?
