# 0099: The map from the registry's option keys to the catalogue's option codes

Status: Proposed; owner questions listed
Date: 2026-10-30
Plan step: plans/platform-v5.md section 6 item 3 (an orchestrator wiring task, nobody's workstream).
Migration: `supabase/migrations/20261201040000_option_code_map.sql`.

## Context

Two vocabularies describe the same garment and nothing joined them.

- The **garment registry** (`lib/garment/registry`) asks a designer nine questions about a jersey and stores the
  answers in the designer's own words: `neckline: "crew"`, `cuffs: "rib-cuff"`, `collar: "none"`. Every design made
  before the catalogue existed holds those words, and `toDesignObjectV2` copies them straight into the design
  object's `article.options` (`lib/design-object/to-v2.ts`).
- The **base article catalogue** (decision 0066) holds the options a factory approved, by code: `C01`, `C02`, `C03`
  for the neck finish, `K01` and `K02` for the sleeve finish, `P00` to `P02` for the pattern fill. The spec wants
  the factory and the club to use one reference: "Codes come from the catalogue (`option_def.value`), so the factory
  and the club use the same reference" (`docs/spec/02-features.md`).

Until now the production package's option field wrote **the design's own word** with `R-GAP-000` and the sentence
"not yet mapped to a catalogue code" (decision 0070's "The registry's option keys are not catalogue codes"). A
factory file therefore named an option in Knitwright's words — `none (not yet mapped to a catalogue code)` in the
field headed `Option: collar` — where a code the catalogue approved belongs. Worse, it read the design's `collar`
answer into the catalogue's `collar` group, and those are **two different questions**: the catalogue's `collar`
group is the neck finish (rib or binding), while the registry's `collar` key asks whether there is a stand collar at
all. The field was answering one question with the answer to another.

## Decision

1. **The map is data, in the shape the catalogue already uses.** `public.option_code_map`, one row per question:
   platform data, read by signed-in members, written only by the server's key, no insert, update or delete policy —
   the same idiom and the same grants as `option_defs`. The seed is generated by `lib/option-codes/seed/sql.ts` from
   `lib/option-codes/seed/rows.ts` into the migration's seed markers, and `seed/sql.test.ts` fails if the two drift,
   exactly as `lib/catalogue/seed/sql.ts` seeds the catalogue's own approved options. Nothing is a literal in a
   component, and the app reads rows.

2. **A row joins a registry choice to a code only where a published file says they are the same thing, and quotes
   it.** `sources` is a jsonb list of `{file, quote}`, and `seed/rows.test.ts` reads every cited file and fails if
   the quote is not in it word for word. The cited files are the build pack's own: the article's `article.json`, its
   `rulebook.md`, its `README.md`, its 17-page tech pack and `ONBOARDING.md`. A citation that is not under
   `docs/spec/` fails the same test, so our own source files can never stand as a source.

3. **The database refuses an invented code, not just our code.** A mapped row's `(article_id, option_group,
   option_code)` is a foreign key into `option_defs (article_id, option_group, code)`, so a row can only ever name a
   code the catalogue really approved **for that article and that group**. A check constraint adds the rest: a
   `mapped` row must name a code, a group, a key, a choice and at least one source and carry no note; a
   `no_code_yet` row must name no code and no source and must carry a note.

4. **Three kinds of row, because "no code" has two different meanings.**
   - `mapped` — the registry choice is this catalogue code.
   - `not_an_option` — the catalogue carries the question somewhere other than an option code, so **no code is
     owed**: fit is an article attribute (`base_articles.fit`), a set-in sleeve and a short sleeve are what the
     article *is*, and a hem that drops at the back is the parameter `back_drop_tail`. Each such row still cites the
     published source that says so.
   - `no_code_yet` — nothing published joins them. The row carries no code, keeps `R-GAP-000`, says in words what
     is missing, and becomes an owner question below.

5. **The group's own name is not the registry key that feeds it.** `codeForGroup` reads a group only through the key
   the map binds to it: the catalogue's `collar` group is answered by the registry's `neckline`, never by its
   `collar`. A test proves that a design asking for a band collar still reports the neck finish its neckline chose.

6. **The tech pack says plainly where there is no code, and never writes the design's word as one.**
   `lib/kpp/input/fields.ts` now reads the map. A field carries `C02 V-neck, …` where the design chose the code or
   the map resolves it from the design's word; where nothing joins them it reads
   *"No catalogue code yet: the design asked for "band-collar" under the design option "collar", and nothing
   published joins it to a code."* with `R-GAP-000`. A choice the catalogue has no group for at all gets a field of
   its own (`Design option: collar`), because the alternative is that the choice leaves no trace in the factory's
   file. A design that said nothing about a group still gets the article's own default, labelled `from_base`, as
   before: that is the catalogue's data, not a guess.

7. **`optionCodeMap` is a required field of `KppRows`.** Nothing mounts the package route yet (decision 0070,
   plan v5 X5b), so making it required costs no caller today and means whoever mounts it must hand the builder the
   real rows rather than silently shipping a package with no codes.

## The map, row by row (JSY-SS-01)

Only `JSY-SS-01` is mapped: it is the only article with option codes at all, because the other seven launch
articles are seeded with none (decision 0090). Its registry types are `football-shirt` and `team-jersey`
(`lib/catalogue/registry-map.ts`), and between them they ask nine questions. Every one has a row.

### Mapped (4)

| Registry key | Choice | Group | Code | Source |
|---|---|---|---|---|
| `neckline` | `crew` | `collar` | **C01** | `README.md`: "Only the default options are drafted (crew neck C01, hem K01, no parameter offsets)."; tech pack page 1: "Short sleeve, set-in sleeve, crew neck (C01), straight hem"; `article.json` C01 is the default crew neck; `rulebook.md` R-CON-004 |
| `neckline` | `v-neck` | `collar` | **C02** | `rulebook.md` R-CON-005: "Collar C02 \| V-neck with 15 mm self-fabric binding and a mitred V"; R-FIT-007: "V-neck C02 uses a 140 mm front drop"; `article.json` C02 |
| `cuffs` | `none` | `sleeve_finish` | **K01** | `rulebook.md` R-CON-007: "Hems K01, body \| 2-needle coverstitch (ISO 406), 6.4 mm gauge; sleeve 20 mm, body 25 mm"; `README.md` names the article's default sleeve finish as "hem K01"; `article.json` K01 is the default |
| `cuffs` | `rib-cuff` | `sleeve_finish` | **K02** | `rulebook.md` R-CON-008: "Cuff K02 \| 1x1 rib cuff, 25 mm finished"; R-COST-002: "Rib cuffs (K02), V-neck (C02) and drop tail add sewing time"; `article.json` BOM: "Neck rib (C01) or cuffs (K02)" |

### No code owed, and the source that says so (8)

| Registry key | Choice | Where the catalogue carries it |
|---|---|---|
| `fit` | any | An article attribute: this article is one fit, and `base_articles.fit` holds it (`article.json` name, R-FIT-001). Another fit is a validation matter, not a missing code. |
| `sleeve-type` | any | The article is set-in by definition (`article.json` name and construction step 4, tech pack page 1). A raglan jersey is a different block. |
| `sleeve-length` | any | The article is the short-sleeve jersey; the long-sleeve one is its own article, `JSY-LS-01` (ONBOARDING.md). |
| `collar` | `none` | The article has no collar at all: its neck is finished by the `collar` group's own codes. |
| `placket` | `none` | The published description of the whole garment names every feature it has and no placket. |
| `side-panels` | `none` | The same description names no side panel. |
| `hem-shape` | `straight` | The article's hem is straight (tech pack page 1, POM K "Hem width, half (straight body)"). |
| `hem-shape` | `curved` | The parameter `back_drop_tail`, 0 to 40 mm (R-PAT-005), not an option code. |

### Deliberately unmapped: nothing published joins them (6)

| Registry key | Choice | Why |
|---|---|---|
| `collar` | `band-collar` | No published source names a code for a stand collar on this article. The catalogue group called `collar` is the neck finish, not a collar. |
| `placket` | `buttons` | No published source names a placket code. |
| `placket` | `zip` | The same. |
| `side-panels` | `contrast-insert` | No published source names a contrast side-panel code. |
| `hem-shape` | `side-vent` | No published source names a code **or** a parameter for a side-vented hem. |
| — (the group `pattern_fill`) | — | **No registry key records the pattern at all**: a design's pattern is drawn as artwork layers, so no registry choice maps to `P00`, `P01` or `P02`. The package reports the article's own default and labels it `from_base`. |

`C03` ("Crew neck, self-fabric binding 15 mm") is an approved code **no registry choice can reach**: the registry's
`neckline` records the neck's *shape* and the catalogue's `collar` group records shape *and* finish, so `crew` cannot
tell C01 from C03. It is mapped to C01 because every published source that names this article's crew neck names C01
(the README's drafted default, the tech pack's first page, `article.json`'s `default: true`), and none names C03
against any designer-facing word.

## Not done, and why

- **Nothing reads the map at runtime yet.** `buildKppInput` has no caller: X5b built the production package but
  deliberately did not mount its export route, because `PrintSource` is still unwired (decision 0070 revision 2,
  plan v5 section 6 item 1). `optionCodeMap(client, code)` is the read whoever mounts it calls. The map is otherwise
  unused on purpose: this change touches one field.
- **The seven other launch articles are not mapped**, because they have no option codes to map (decision 0090).
  When their briefs gain options, each gains rows here with its own citations.
- **Decision 0070's paragraph "The registry's option keys are not catalogue codes" is now superseded** by this
  record. It is X5b's decision record, so it is left for its owner to revise rather than edited here.
- **The editor writes codes already.** `lib/editor/form.ts` (Y2) stores `options[group] = code`, so designs made in
  the new editor need no map. The map exists for designs made before the catalogue and for the registry's own
  questions the catalogue has no group for.

## Owner and factory questions

1. **`JSY-SS-01` has no code for a band collar, and `team-jersey` offers one.** A design can ask for a band collar
   today and the catalogue cannot name it. Is a band collar an option of this article (so it wants a `C04`), or is
   it a different article? Registry key `collar`, choice `band-collar`, article `JSY-SS-01`.
2. **No code for a placket, and the jersey offers buttons and a zip.** Registry key `placket`, choices `buttons`
   and `zip`, article `JSY-SS-01`. Same question: a code on this article, or a different article?
3. **No code for a contrast side panel.** Registry key `side-panels`, choice `contrast-insert`, article
   `JSY-SS-01`. A sublimated jersey's side panel may be only a colour in the artwork rather than a cut piece; if it
   is a cut piece it needs a code and a pattern.
4. **No code or parameter for a side-vented hem.** Registry key `hem-shape`, choice `side-vent`, article
   `JSY-SS-01`. `back_drop_tail` covers the curved hem; nothing covers a vent.
5. **Nothing records the pattern as a catalogue code.** `P00`, `P01` and `P02` exist and no design can choose one,
   because the pattern is drawn as artwork. Should the editor also record a `pattern_fill` code beside the artwork,
   or should the codes go? Until this is settled, every package names the default `P00` from the base, which is the
   article's own data but is not a statement about the artwork.
6. **`C03` cannot be reached from any designer-facing word.** The registry has one crew neck and the catalogue has
   two. Should the registry gain a neck-finish question (rib against self-fabric binding), or should `C03` wait for
   the editor's own tiles?
7. **A raglan sleeve, a long sleeve and a slim or relaxed fit are offered by the registry and are not this
   article.** They are recorded here as "no code owed" rather than as gaps. Whether a design that asks for one
   should be refused is X4's validation question, and it is not refused today.
