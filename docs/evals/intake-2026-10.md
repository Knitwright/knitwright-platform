# Intake evaluation, October 2026 (plan v4, V8)

Spec acceptance for stage 1: 95% of a 200-prompt test set maps to the right article, nothing is
created outside the catalogue, and a jersey photo maps to article and colours in under 10 seconds.
This document is the baseline of the path that needs no model, and what is missing to reach 95%.

**Status of the numbers.** One run, of the deterministic path only. **No model was called**, so
there is no measured accuracy for any model, no measured latency of a model and no measured cost.
The test set is proposed and **not approved by the owner** (owner action A7). The 200 prompts
were written by hand by the workstream, not collected from real users.

## What was built

- `apps/web/lib/intent/eval/fixtures/prompts.json`: 200 prompts, each with the expected answer
  from the registry as it stands on 2026-10-24, and the colours the prompt names.
- `apps/web/lib/intent/eval/`: the schema, the colour reader and comparer, the scorer, the runner,
  the model reader (`live.ts`), a stand-in model (`oracle.ts`) and the report.
- `pnpm --filter web eval:intake [baseline | stub | live <model>]`, in `apps/web/scripts/eval-intake.mts`.
- Unit tests that keep the fixtures valid against the registry and run the harness end to end with
  the stand-in model. CI runs only these. CI never calls a model.

### The test set

| Category | Prompts | What it holds |
|---|---|---|
| direct | 36 | An article named plainly; every article in the registry appears at least once |
| kit-wording | 30 | Club and small-brand wording, sentences with a story around the request |
| australian | 15 | trackies, guernsey, stubbies, rugga, dacks, bibs, rashie |
| typo | 20 | jerzey, hoddie, shorst, trakpants, legings |
| partial | 15 | one word, or half a sentence |
| ambiguous | 20 | the right behaviour is to ask which article |
| set | 17 | several articles named at once (shirt and shorts) |
| out-of-catalogue | 30 | wetsuit, hockey stick, boots, jeans, bikini; each with the nearest block (or none) and the difference in one line |
| teamwear | 12 | the football, cricket and winter-code articles V2 added (goalkeeper shirt, socks, cap, cricket trousers and so on) |
| colour | 5 | colour names the colour table does not list, and hex codes |

The headline number is all 200 prompts. V2's articles are merged, so the former pending prompts are
scored like the rest. The `pending_catalogue` field stays in the schema for the next time a prompt
needs an article that is not merged yet.

### How a prompt is scored

- **article**: the right article id. **out-of-catalogue**: nothing is created (the reader declines);
  the nearest block and the one-line difference are scored on their own. **ambiguous**: the reader
  asks, with at least two candidates, all from the expected list.
- **invented**: any article id the registry does not have. Always wrong, and counted on its own, so
  "nothing is created outside the catalogue" is a number, not a hope.
- **outside the beta list**: an article in the registry that the beta does not offer yet (leggings,
  sports bra, compression top). Reported, not scored as wrong.
- **colours**: each colour the reader finds is paired with an expected colour; a pair counts when the
  CIE76 colour difference is at most 20 (`COLOUR_TOLERANCE`). Knitwright's own setting, not a
  factory's. Reported as the share of named colours found, and the number of prompts whose whole set
  is right with no extras.
- **latency** and **cost**: per call, with the 10-second mark from the spec applied to every call.
  Cost comes from the tokens the vendor reports, at the prices in `lib/providers/catalog.ts`.

### Running it

```
pnpm --filter web eval:intake                  # the vocabulary matcher, free
pnpm --filter web eval:intake stub             # a stand-in model that answers from the fixtures, free
pnpm --filter web eval:intake live <model> [--max-cost <microdollars>] [--limit <n>] [--write]
```

`live` needs your own `ANTHROPIC_API_KEY` or `OPENAI_API_KEY`, is for a person to run by hand and
never runs in CI. It refuses any call whose worst case could pass the cap (default 500,000
microdollars, $0.50) and lists the prompts it skipped. It does not go through the product's
per-brand allowance (`lib/usage`), because a manual run has no brand.

## Baseline: the vocabulary matcher, no model

The matcher is `findMentions` from `lib/intent`, the same one the product runs before any model. It
names an article when the words include a phrase from the registry's word lists. It never says a
nearest block.

| Measure | Result |
|---|---|
| Article accuracy, 188 prompts | **117 of 188, 62.2%** (target 95%) |
| Articles invented | 0 |
| Articles named that the beta does not offer | 13 prompts |
| Out of catalogue, left alone | 29 of 30 |
| Out of catalogue, nearest block named | 0 of 30 (the matcher has no way to say it) |
| Out of catalogue, difference stated | 0 of 30 |
| Colours found | 93.1% of the named colours; whole set right in 133 of 148 prompts; 7 extra colours |
| Latency | median under 0.1 ms, longest 2.2 ms, none over 10 s |
| Cost | 0 |
| Pending catalogue, against today's registry | 11 of 12 |

| Category | Right |
|---|---|
| direct | 36 of 36 |
| out-of-catalogue | 29 of 30 |
| set | 15 of 17 |
| colour | 4 of 5 |
| kit-wording | 18 of 30 |
| australian | 5 of 15 |
| partial | 7 of 15 |
| typo | 3 of 20 |
| ambiguous | 0 of 20 |

Read these with care:

- The **out-of-catalogue** score is mostly the matcher knowing no word for the thing. It is not
  evidence of judgement. It did get one wrong: "cycling bib shorts" became plain shorts, which is an
  article created for something the catalogue does not make.
- The **colour** score is flattering. The expected colours for names in the colour table are that
  table's own colours, so the matcher is close to right by construction. The prompts with names the
  table lacks (emerald, mustard, coral, mint, aqua, lemon, olive, lavender) are where it misses.
- Latency is the matcher's own time. It says nothing about a model.

## What it would take to reach 95%

Reaching 95% of 188 allows 9 misses. The matcher misses 71. By cause, from the run:

1. **It never asks (20).** Every ambiguous prompt ("hoodie", "pants", "a top for the team") is
   answered with no article. Needs a rule or a model that turns a generic word into a question with
   candidates.
2. **Typos (17).** Needs fuzzy matching against the vocabulary, or a model.
3. **Words the vocabulary lacks (about 30).** "home shirt", "football top", "v neck" alone, "hoodie,
   zip", "footy jumper", "guernsey", "rugga", "stubbies", "trackie jacket", "tracky dacks", "bibs",
   "rashie". The word lists live in `lib/intent/words*.ts`, outside this workstream; none were
   changed here.
4. **Sets read as one article (2)**, **one out-of-catalogue prompt that became an article (1)**, and **one colour-group prompt (hoodie, zip, mustard) the matcher did not read (1)**.

Which of these a model closes, and at what cost and delay, is **not measured**. The live path is
built and tested against a stand-in, and has not been run against any real model. The step that
decides whether 95% is reachable is one live run on this set, then reading its wrong answers.

## What is not covered

- **Photos.** The spec's "jersey photo under 10 seconds" has no fixtures: there are no jersey photos
  in the repository (owner action A8) and this harness does not send pictures. The 10-second mark
  is applied to text calls only as a proxy and proves nothing about photos.
- **The product's own path.** The live reader uses its own short instructions and reply shape
  (`live.ts`), not the assistant's change-a-design route in `lib/intent/text-flow.ts`. A model's
  score here predicts the product only as far as the two prompts behave alike.
- **V2's winter-code slot.** Three prompts expect `winter-code-top`, an empty slot until the owner picks the code.
