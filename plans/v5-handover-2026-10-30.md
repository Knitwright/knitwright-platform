## 8. How to run the agents — this part is hard-won

- **Every agent must be launched with `isolation: "worktree"`.** Without it an agent runs in the
  primary checkout and several of them share one working tree and switch branches inside it. That
  happened: one workstream's committed migration vanished from the tree mid-run, and another's commit
  landed on a different workstream's branch. Both were recovered, by luck and by the agents noticing.
- **No agent may start local Supabase.** `supabase/config.toml` pins one project id and fixed ports
  (54321/54322) and the plan forbids editing it, so there is exactly **one** database on this machine,
  shared by every agent. Tell each agent: no `podman`, no `pnpm db:start`, no `db:reset`, no `db:env`.
  Their local gate is `pnpm install`, `typecheck`, `lint` and the unit tests of their own directories.
  They still **write** database and browser tests; CI is the only place those run, and it is the
  authority. The orchestrator alone uses the local stack, one failure at a time, for debugging.
- **Agents cannot run in the cloud.** `claude --cloud` refuses a non-interactive invocation — "run
  locally and would silently ignore --cloud" — and every tool call a session makes is non-interactive.
  That is also why `isolation: "remote"` silently degrades to a local worktree. A cloud session cannot
  be a subagent of a local orchestrator. The only way to get genuine cloud execution is the owner
  running `claude --cloud "<brief>"` from a real terminal, one session per workstream. The account is
  fully provisioned for it (claude.ai auth, Max plan, `gh` with `repo` scope, `/web-setup` done).
- **Tell every agent to commit and push after every step.** Three sessions have now died or been cut
  off mid-wave. A crash must cost one step, not a workstream.
- **Usage limits are the real pacing constraint.** Fourteen concurrent agents exhausted a five-hour
  limit in about an hour. Keep enough headroom to merge and fix, or the wave stalls with everything
  half-done. An interrupted agent's work is saved and it can be resumed with a message — but only
  within the session that spawned it. A new session must relaunch the workstream from its brief.

## 9. Traps that cost real time, now in the plan's Lessons

- `signIn` in `apps/web/e2e/support.ts` only presses the button; the session cookie arrives with the
  redirect. Follow it with `await expect(page).toHaveURL(/\/studio$/)` before navigating, or the test
  runs as a signed-out visitor and every guarded page answers 404. This made three X8 failures look
  like a broken page.
- CI retries a failed browser test once, so anything a locator filters on must be unique per run, or
  the retry trips over the row its own failed attempt left behind.
- `ops_cut_batches` groups by factory, fabric, article and cut-off and **reuses** a batch it has
  already cut. `ops.spec.ts`, `ops-qc.spec.ts`, `journeys.spec.ts` and `job-packet.spec.ts` all submit
  the same `knitwright-default` / `mesh-140` / `crew-tee` order, so a fixture using that key is handed
  *their* batch. Give each fixture its own fabric. This surfaced three separate times.
- A `loading.tsx` flushes the shell before the page runs, so `notFound()` can no longer set a 404
  status — the route answers 200.

## A contradiction that is already shipped (decision 93) — do not fix it blind

`guardrails.safe_zone_mm` defaults to **10 mm**, labelled `knitwright-default`

  the rulebook has **no source to be labelled with**. It needs a third source value and its wording
  before the number can move honestly.
- the registry entry already carries `question: 15`, so the intended answer is on record.
- `lib/panel-layers/edges-y3.test.ts` and `lib/settings/registry.test.ts` assert the 10.

So: add the rulebook source, then move the default to 15 and update those two tests. One small PR,
but it changes what the guardrail passes, which is why it is the owner's call and not a drive-by.
